# P0. Running AI Security at a Company

## What this part is

The [main course](https://github.com/rajumandala/aisec-notes/blob/main/00.%20Syllabus.md) secured one AI order assistant inside a broker's trading app, with its controls in code. [Part S](https://github.com/rajumandala/adlc/blob/main/notes/S0.%20AI%20in%20the%20SDLC.md) looked at the team that builds it with AI, and [Part M](https://github.com/rajumandala/ai-supplychain/blob/main/notes/M0.%20Model%20Supply%20Chain.md) at the models it depends on. All three looked at one system.

This part looks at the whole company. The broker now has many AI features from many teams, and a small security team. The questions change from "is this assistant safe?" to:

- Which controls should every team get for free, and which must each team build for its own business?
- Which features need a deep review, and which need none?
- How does the company know it is getting safer, and what does it report?
- What has gone wrong at other companies, and what would have stopped it?

The example stays the same broker, with the same people and the same controls. Where a control was built in the main course, the notes link to it.

## How the notes are built

The notes follow the same pattern as the earlier parts:

1. Each note starts from the problem the previous one ended on.
2. It adds one company-wide practice: a shared service, a process or a measure.
3. It shows the point with an example from the broker. Most of this part is design and process, so there is little code, and none of it has been run.
4. It lists the OWASP risks it meets, each with an example, the issue and the fix.
5. It ends on the next problem and links to the note that deals with it.

## The concepts

| P1 | [The AI security platform](P1.%20The%20AI%20Security%20Platform.md) | Shared services for every AI feature: an AI gateway, guardrails, an MCP registry, agent identity, retrieval, sandboxes and evals | The platform owns who is calling, which model, what leaves and what is recorded; the app owns what each action may do. Direct provider calls are blocked, so the gateway is the only way out. The gateway is now the most sensitive system, and it sees text, not meaning | LLM02, LLM06, ASI04, ASI03 | Features are not equally dangerous, and the security team has time for only a few deep reviews | Note written, not run |
| P2 | [Intake and risk tiers](P2.%20Intake%20and%20Risk%20Tiers.md) | A short intake for every AI feature, including vendor AI, and a tier computed from facts: what it can do, what data it touches, what untrusted text it reads, whether anything can leave, who uses it | The tier comes from platform registries, not the team's opinion. The lethal trifecta or acting alone is tier 3 on its own. The cheapest way down a tier is a design change. The tier is recomputed on every new scope, tool, source or way out, and a higher tier blocks the deploy. Unregistered gateway keys, blocked provider calls and vendor settings find the rest. The business owner signs the remaining risk, and the acceptance expires | LLM03, LLM02, LLM04, ASI03 | The company cannot yet show that it is safer than last year | Note written, not run |
| P3 | [Metrics and roadmap](P3.%20Metrics%20and%20Roadmap.md) | Measures for coverage, effectiveness and exposure, a one-page board report, and a roadmap built from the gaps | Counting reviews and blocked prompts says nothing. Coverage comes from the registries and its target is 100%. Attack success rate on a fixed suite gets tuned to, so add a fresh suite and count attacks stopped by code, not by the model. Canaries and drills measure time to detect and time to stop. Since injection is unsolved, measure the worst case if the model is fully controlled, and fix features where it is unbounded | LLM01, LLM03, ASI10, LLM06 | The team writes its own tests, and the broker has had no serious incident to learn from | Note written, not run |
| P4 | [Incident case studies](P4.%20Incident%20Case%20Studies.md) | Eleven public AI incidents (Chevrolet, Air Canada, Slack AI, GitHub MCP, EchoLeak, ForcedLeak, Replit, Amazon Q, Salesloft Drift, Samsung, ChatGPT), each mapped to a pattern, a control and a test, and an incident response plan for AI | Every case where the model was fooled also had a way out, a broad token or an unchecked answer. Several needed no model at all. The soft controls failed, and a hard control failed when nobody maintained it: an allowlisted domain expired. Each case ends as an eval case, and poisoned memory, indexes and summaries must be cleaned after an incident | LLM01, LLM07, LLM03, ASI04 | Vendors patch the way out, never the model following the attacker's text | Note written, not run |
| P5 | [Why prompt injection is unsolved](P5.%20Why%20Prompt%20Injection%20Is%20Unsolved.md) | An answer to "why can't the provider fix it?", the research defences at four levels, and how to judge a defence's numbers | SQL injection was solved by a separate channel; a model has one token stream, and roles are trained habits. Reading instructions in data is part of the job, intent is not in the text, and the attacker moves second. Spotlighting, instruction hierarchy, StruQ and SecAlign, and classifiers lower the rate; adaptive attacks broke most published defences. Only system-level designs such as CaMeL give guarantees, at a cost in usefulness. Model gains never move a feature down a tier | LLM01, ASI01, LLM03 | Regulators, auditors and customers ask in their own frameworks | Note written, not run |
| P6 | [Standards map](P6.%20Standards%20Map.md) | One control list with owners and evidence, mapped to NIST AI RMF and its Generative AI Profile, ISO/IEC 42001, the EU AI Act and MITRE ATLAS | Each framework does a different job: guidance, a certifiable management system, law, an attack knowledge base. Map from the controls outwards, and take evidence from the platform once. EU AI Act Annex III duties now start in December 2027 after the Digital Omnibus. Compliance is not security: every framework can be met by a feature with the lethal trifecta, and a certificate covers a management system, not a model | LLM01, LLM02, ASI04 | End of Part P | Note written, not run |
