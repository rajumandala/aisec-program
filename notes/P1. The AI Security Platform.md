# P1. The AI Security Platform

The main course ended with one assistant: reviewed, watched and governed. A year later the broker has thirty AI features from fifteen teams: the order assistant, support-desk drafts, research summaries, a KYC document reader, an internal HR bot, coding agents for its developers, and a few nobody in security has heard of. Each team would have to know all of the main course to get each one right, and the security team cannot review thirty designs a quarter.

## The idea

Every control in the main course was built **inside the app**. That works for one app. For thirty it fails in three ways:

- **Each team rebuilds the same controls,** and some get them wrong. One forgets `store=False`, another puts the API key in the mobile app, a third forwards every tool from an MCP server.
- **Reviews become the bottleneck.** If every feature waits for a security review, teams either wait or skip it.
- **Nobody can answer company-wide questions.** Which apps send client data to which provider? Which agents can place orders? What would the kill switch turn off?

The answer is a **platform**: move the controls that are the same in every app into shared services that every team uses, and leave in each app only the decisions that depend on its own business. In AppSec terms, it is the move from reviewing every login form to giving every team the same identity provider.

The rule for what goes where:

> **The platform owns who is calling, which model, what leaves, and what is recorded. The app owns what this action is allowed to do.**

This is Part P of the series. It is about running AI security across a company, not about one assistant. It has no code that runs on its own, and nothing in it has been run.

## Step 1: sort the controls

Go through the main course and ask, for each control, whether it is the same in every app:

| Control from the main course | Same in every app? | Where it lives |
|---|---|---|
| Provider keys, approved models pinned by snapshot, `store=False`, region (notes 1, 14, 14a) | Yes | **AI gateway** |
| Budgets and rate limits per user and per app (notes 4, 10) | Yes | **AI gateway** |
| Traces with pseudonyms, audit records (notes 14a, 15) | Yes | **AI gateway**, plus the app's own audit events |
| Removing invisible characters; PAN patterns; no images; allowed links (notes 10, 10a) | Yes | **Guardrail service**, called by the gateway |
| Approved MCP servers, pinned tools, names per server (notes 6, 6a) | Yes | **MCP registry and gateway** |
| Agent tokens with `sub` and `act`, scopes, revocation, mandate grants (notes 12, 12a) | Yes | **Agent identity service** |
| Search filtered by the reader's permissions (note 7a) | Yes | **Retrieval service** |
| Sandboxes for model-written code and queries (note 9) | Yes | **Code execution service** |
| Evals and red-team cases in the build pipeline (notes 5, 10) | The runner, yes; the cases, no | **Eval service**; each team writes its own cases |
| `check_order`, the confirmation wording, typed preferences, mandate limits, the agent split (notes 2, 4, 8, 9, 10b, 12a) | **No** | **The app** |

The last row is the important one. A platform cannot know that an order above ₹5 lakh is a fat-finger, or that a request that read news must not place an order. Those are business rules, and they stay with the team that owns the business.

## Step 2: the AI gateway first

Build the gateway first, because every model call passes through it, so it gives the most control for one piece of work. Every app calls it instead of the provider:

```python
client = OpenAI(base_url="https://ai-gateway.broker.internal/v1",
                api_key=TEAM_KEY)              # a key for this team and app, issued by the gateway
```

For the team, that is the only change. Behind it, the gateway:

- **Holds the provider keys.** Teams never see them. A leaked team key works only through the gateway, with that team's budget and models, and can be revoked in one place.
- **Allows only approved models, by exact snapshot.** A provider moving an alias does not change thirty apps overnight (note 14a).
- **Sets the provider options the company decided on:** storage off, region, safety identifier (note 14). A team cannot forget them.
- **Enforces budgets** per app and per end user (note 10).
- **Runs the guardrails that are the same everywhere:** invisible characters out on the way in, PAN patterns and images out on the way back (notes 10, 10a).
- **Records structure, not content,** in one trace format, with pseudonyms (note 14a).
- **Has a kill switch per app and per model.** Note 14's kill switch now works for every feature, and "turn off every app using model X" is one setting.
- **Knows every caller.** The list of team keys is the inventory of AI features that nobody had before.

To make the gateway the only way out, production networks **block direct calls to model providers**. That one rule is the hard enforcement. Everything else on the platform is adopted because it is easier, but a provider call that does not go through the gateway simply fails.

Two warnings:

- **The gateway is now the most sensitive system in the company.** It sees every prompt from every app and holds every provider key. Note 14 listed "who else is in the path" as a question to ask about a provider. The gateway is the answer for every app, so it gets the strictest access, change control and monitoring the company has.
- **The gateway sees text, not meaning.** It cannot run `check_order`, and it does not know whether a request read news. It sets a floor for every app. It is not the security of any one app.

Build or buy: open-source and commercial AI gateways exist, and cloud providers offer their own. The proxy itself is rarely worth writing. The policy is: which models, which options, which budgets, which guardrails, what is logged. Own that, keep it in version control, and review changes to it like changes to `check_order`.

## Step 3: the MCP registry and the agent identity service

The next two services cover what agents connect to and who they act as.

**The MCP registry** is note 6a's approved list, made into a system:

- Each entry has an owner, a pinned version, the tool fingerprints from note 6, the scopes it needs and the data it can reach.
- Agents in production connect through an **MCP gateway** that checks the pins on every start, names tools after their server, routes by the reviewed table and logs every call (note 6). A server that is not in the registry cannot be reached.
- Developer machines get the same list through managed settings in their AI tools (note 6a).

**The agent identity service** is note 12, made into a system:

- Every agent is registered with a name, an owning team, the scopes it may ever ask for and how much it may do on its own: proposes only, acts after a confirmation, or acts within a mandate (note 12a).
- It issues the short-lived tokens with `sub` and `act`, and holds the mandate grants. Revoking a user's consent or a whole agent happens in one place.
- The registry of agents is the second inventory: every agent that can act, who owns it, and what it can do.

## Step 4: adoption, not policing

A platform nobody uses is a diagram. Teams adopt it when it is the easiest way to ship:

- **A starter template** gives a new AI feature the gateway, an agent identity, tracing, an eval pipeline with the company's standard security cases, and the review questions from note 10b as a checklist in the pull request. Starting from the template takes minutes. Building outside it takes weeks.
- **One hard rule, many soft ones.** Direct provider calls are blocked. Everything else is a default that a team can change, with a reason, in a reviewed file. That turns "security said no" into "this team chose X, and it is written down".
- **Exceptions expire.** A team that needs a model outside the approved list gets it for 90 days, with an owner and a date, like note 6a's beta scope.
- **Review where the risk is.** The platform removes most of the repeated review work. The security team spends its time on the features that act: orders, mandates, money and data leaving the company. P2 shows how to decide which those are.

## Step 5: what the platform must not own

A platform team can make the company less safe if it takes on the wrong jobs:

- **Business rules.** If the platform team writes the limits for orders, nobody who understands orders reviews them. The app team owns `check_order`, and risk management owns its limits (note 15).
- **Risk acceptance.** The platform reports a gap. The business owner of the feature decides whether to accept it.
- **The claim that apps are safe.** "It goes through the gateway" becomes a reason to skip design reviews. The gateway's guardrails are mostly soft (note 10a), and none of them stops an agent with the trifecta from acting (note 10b). The template's checklist says so in its first line.

| Service | Covers, for every app | Does not cover |
|---|---|---|
| AI gateway | Keys, models, provider options, budgets, common guardrails, traces, kill switch, inventory | Business rules; whether a request read untrusted text |
| Guardrail service | Invisible characters, PII patterns, images and links, classifiers | Anything a classifier misses; actions |
| MCP registry and gateway | Approved servers, pins, names per server, call logs | What the agent does with a tool result |
| Agent identity service | Agent inventory, scoped tokens, consent, revocation, mandate grants | Whether a mandate's limits are sensible |
| Retrieval service | Permission filtering, source checks, deletions | Whether the source's own permissions are right |
| Code execution service | Sandboxes for code and queries | What the code's output is then used for |
| Eval service | Runs every team's cases on every change | Writing the cases |

## OWASP risks in this note

The codes come from the [OWASP Top 10 for LLM Applications](https://github.com/rajumandala/aisec-notes/blob/main/A1.%20OWASP%20Top%2010%20for%20LLM%20Applications.md) and the [OWASP Top 10 for Agentic Applications](https://github.com/rajumandala/aisec-notes/blob/main/A2.%20OWASP%20Top%2010%20for%20Agentic%20Applications.md), both 2026 editions. Nothing in this note has been run, so each example shows what would happen.

### LLM02: Sensitive Information Disclosure

- **Example:** The HR bot's team calls the provider directly with default settings, and every employee question is stored by the provider for 30 days.
- **Issue:** One team's default becomes a company-wide data flow that nobody listed.
- **Fix:** Direct provider calls are blocked; the gateway sets storage off and the region for every app.

### LLM06: Unbounded Consumption

- **Example:** A new feature loops on a bad prompt over a weekend, with a provider key copied from another team.
- **Issue:** The cost lands on the wrong team, and nobody can stop one app without stopping all of them.
- **Fix:** A key per app, budgets per app and per user, and a kill switch per app on the gateway.

### ASI04: Agentic Supply Chain Vulnerabilities

- **Example:** Three teams connect the same community MCP server, each at a different version, one of them unpinned.
- **Issue:** Nobody knows which agents use it, so nobody can update or remove it when it changes.
- **Fix:** The MCP registry with owners and pins, and an MCP gateway that refuses servers not in it.

### ASI03: Identity and Privilege Abuse

- **Example:** Each team gives its agent a service account, and two of them can read every client's holdings.
- **Issue:** The confused deputy from note 12, repeated across the company.
- **Fix:** The agent identity service issues per-user tokens with `act`, and registers what each agent may ever ask for.

## Problem and next step

**Problem:** the platform makes the common controls cheap, and it shows every AI feature in one list. But the features are not equally dangerous. A research summary and a mandate that sells shares cannot get the same review, and the security team has time for only a few deep reviews a quarter. Who decides which features need which controls?

**Next, in [P2. Intake and Risk Tiers](P2.%20Intake%20and%20Risk%20Tiers.md): classify every AI feature by what it can do, what data it touches and who is watching, and let the tier decide the controls and the review.
