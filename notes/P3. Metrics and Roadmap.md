# P3. Metrics and Roadmap

P2 ended with a platform, an intake and a tier for every AI feature. The board then asks a simple question: is the company safer with AI than it was a year ago? "We did 40 reviews and blocked 2 million prompts" does not answer it. The first number is work done, and the second could mean the guardrail is good, or noisy, or that attacks went up.

## The idea

A security metric is useful when it changes a decision. For AI that means measuring three things, in this order:

1. **Coverage:** do the controls exist where they should? Of the features that need a control, how many have it?
2. **Effectiveness:** do the controls work? When they are attacked or tested, how often do they hold?
3. **Exposure:** if they fail, how bad is it? How much can each feature do when the model is fully controlled by an attacker?

The third one is specific to AI. Prompt injection is not solved (P5), so "how often does an attack succeed?" will never reach zero. The question the main course kept asking is the one to measure: when the model is fooled, what can code still stop? Note 2 put the RMS checks in code for that reason, and note 10b's patterns limit what a fooled model can reach.

In AppSec terms, this is the move from counting scans and findings to measuring coverage, control testing and blast radius.

This note is design and process. Nothing in it has been run, and the numbers in the examples are made up.

## Step 1: what not to measure

Some numbers are easy to collect and say little:

| Number | Why it misleads |
|---|---|
| Reviews done | Work, not risk. It goes up when the team is slow to say no |
| Prompts blocked by guardrails | Goes up with attacks, with false alarms, and with traffic. It cannot tell them apart |
| Red-team findings | Goes up with a better red team. A falling number can mean nobody looked |
| "Jailbreak resistance" scores from a model card | The provider's test, on the provider's model, without our tools or data (note 10) |
| Percentage of staff trained | Says who sat through a course, not who changed a design |

None of these is useless inside the team. None of them belongs on the board's page.

## Step 2: coverage

Coverage numbers come straight from the platform's registries (P1, P2), so nobody has to collect them by hand:

| Metric | From | Target |
|---|---|---|
| AI features known: gateway keys and vendor AI settings with an intake record | Gateway, P2's weekly check | 100% |
| Model traffic through the gateway | Gateway volume against provider bills; block log | 100%, and block log hits trending to zero |
| Tier 3 features with a current threat model, red-team exercise and tested kill switch | Review records | 100% |
| Agents that act with per-user tokens, not shared service accounts (note 12) | Agent identity service | 100% |
| MCP servers in production that are pinned and registered (note 6) | MCP registry and gateway | 100% |
| Tier 3 features with security eval cases that run on every change (note 5) | Eval service | 100% |
| Accepted risks that are past their expiry | Risk register (P2) | 0 |

The targets are all 100% or 0 on purpose. Coverage is not a score to improve slowly. Every gap is a named feature with an owner, and the report lists them.

## Step 3: effectiveness

Coverage says a control exists. Effectiveness says it works. Each of these is a test that runs on a schedule, like note 5's evals:

- **Attack success rate on a fixed suite.** Each tier 3 feature has its own red-team cases from note 10, run on every change and on every new model snapshot. Report the share of attacks where the model did what the attacker wanted. A model upgrade that doubles it is a release blocker, even if every functional test passes (note 14a).
- **A fresh suite as well.** A fixed suite gets tuned to, so its number improves while real attacks do not. A second set of new cases every quarter, written by people who did not write the first, shows whether the improvement is real.
- **Attacks that reached a hard control.** For each failed attack in the suite, did code stop the action (`check_order`, the confirmation, the source label from note 10b), or did nothing need stopping? The share stopped by code should be close to all of them. An attack stopped only because the model resisted is a near miss (note 7).
- **Guardrail misses and false alarms** on a labelled set (note 10a). A guardrail tuned to zero false alarms usually misses most attacks.
- **Time to detect.** Plant a harmless canary: a test news post with an instruction, or a test session that calls tools it never should. Measure how long until monitoring raises an alert (note 14). A signal nobody watches has a detect time of never.
- **Time to stop.** Drill the kill switch and token revocation for one tier 3 feature each quarter (notes 12, 12a). Measure the minutes from decision to the last action stopped.
- **Time from a new public attack to a test case.** When a new technique is published, how long until it is in the eval set? This shows whether the team learns from others (P4).

### Running the red team

These numbers are only as good as the red team behind them. A few rules make it a programme rather than an event:

- **Scope and rules in writing.** Which features, which environments, what is off limits (real client accounts, real orders, the exchange), who to call if something breaks, and who has signed it off. The business owner of each tier 3 feature knows when it is being tested.
- **Production, carefully.** Many failures appear only with the real model, real retrieval and real tools. Test in production with test client accounts, test documents with a marker in them, and order tools pointed at a simulator or blocked by `check_order` limits for those accounts. Everything planted is listed and removed afterwards (P4's clean-up).
- **Tools and people.** Automated tools that send thousands of known attack variants are good for the fixed suite and for catching regressions on every change. People find the new attacks: chaining tools, using the business logic, adapting to the defence (P5). Use both, and do not report the tools' pass rate as the red team's result.
- **Findings have owners.** Each finding goes to the team that owns the feature, with a severity set by what the attack reached (step 4), a fix date, and a test case that must pass before it closes (note 10).

## Step 4: exposure

Exposure asks a different question for each tier 3 feature: **if the model does exactly what an attacker wants, what is the worst thing that happens?** Write the answer down from the code, not the prompt:

| Feature | Worst case if the model is fully controlled | What bounds it |
|---|---|---|
| Order assistant | Proposes a wrong order to the investor who is logged in | `check_order` limits; confirmation of the exact order; no other client's account (notes 2, 3, 4) |
| Morning watcher | Sells within the mandate on a false announcement | Mandate limits, listed sources, run caps, circuit breaker (note 12a) |
| Support drafts | Puts one client's data in a reply to the client who wrote in | Search with the reader's permissions; no links or images (notes 7a, 10a) |
| A new agent with an email tool and client data | Sends any client's data to anyone | Nothing, so far |

This table is the most useful page in the report. It turns "prompt injection is a risk" into a list of bounded and unbounded outcomes, and the last row is the one to fix next. Three numbers summarise it:

- **Features where the worst case is unbounded.** The aim is zero.
- **Features that act alone** (mandates, unattended agents), and the largest amount any one of them can move in a day.
- **Features with the lethal trifecta** (note 10b, P2). Each one is either redesigned or has a signed risk acceptance.

## Step 5: the report

The board gets one page. It has three parts:

1. **Five numbers with their trend:** features known against features with intake; tier 3 coverage; features with an unbounded worst case; attack success rate on the fresh suite for tier 3 features; time to stop in the last drill.
2. **The top three risks in business terms,** each with an owner and a date. "An agent with client data and an email tool has no limit on what it sends. Owner: head of operations. Fix by March." Not "LLM02 in service X".
3. **What the team needs,** such as headcount for tier 3 reviews or a decision to switch off a vendor feature.

Once P7's work starts, a sixth number joins the first part: the share of high-risk actions (contact and bank account changes, large payments, new app grants) that need a passkey or a call back on a known channel.

Engineering teams get the full tables for their own features. The two audiences need different pages, and a page for both serves neither.

Every metric can be gamed. Teams lower their tier by answering intake questions wrongly, which is why P2 checks answers against the registries. A red team fixes on the cases it knows, which is why the fresh suite exists. Watch for a number that improves while nothing changed in the design.

## Step 6: the roadmap

The roadmap comes from the gaps in steps 2 to 4. A simple order works for most companies:

1. **Know what exists.** Inventory, intake, the block on direct provider calls. Every later number depends on this.
2. **Bound the worst cases.** Fix the features with an unbounded worst case, starting with those that act alone or have the trifecta. This usually means design changes, not new tools.
3. **Make the common controls free.** Gateway, agent identity, MCP registry, permission-aware retrieval (P1). Each one moves many features at once.
4. **Test what exists.** Fresh red-team suites, canaries, drills. This is when effectiveness numbers become real.
5. **Raise the bar on new work.** Templates, champions in product teams, tier 2 reviews done by those champions (P2).

Within a step, rank work by how much exposure it removes for the effort, and write down what the team will not do this year and why. A roadmap with no "not doing" list is a wish list.

Two habits keep it honest:

- **Each item names the number it should move.** "Agent identity service" moves "agents with per-user tokens" from 40% to 100%. If nobody can say which number, ask why it is on the list.
- **Expiring risk acceptances feed it.** A risk accepted for six months in P2 comes back as a roadmap item or a new acceptance, not as silence.

## Step 7: who does the work

A roadmap needs owners, and most of the work is not done by the AI security team. A small team that tries to own everything becomes the bottleneck P1 set out to remove.

| Who | Owns | Example from the course |
|---|---|---|
| AI security team | The standards, the tier rules, tier 3 reviews, the red-team suites, the platform's security policy, this report | P2's `tier()`; P3's fresh suite |
| Platform team | Running the gateway, registries, identity service and sandboxes | P1 |
| Product teams | Their features, their business rules, their own security eval cases | `check_order`; note 10's cases |
| Security champions | Tier 2 reviews inside their teams, after training | P2 |
| Data owners | Who may see each system's data; labels | Note 7a; P2 step 6 |
| Privacy and legal | Vendor and provider terms, personal data, the EU AI Act | Note 14; P6 |
| Compliance and risk | Regulators, and the risk register | Note 15 |
| Business owners | Accepting what is left | P2 step 7 |
| SOC and incident response | Detection rules, drills, incidents | Note 14; P4 |

**A governance committee** helps when it is small and decides only what nobody else can: tier 3 risk acceptances above a set size, exceptions that outlive their expiry, and policy changes. It hurts when it reviews every feature. Then it is the bottleneck, and teams build around it (P2 step 5). The tiers decide which features need a review. The committee decides the rules the tiers apply.

**The team itself** is mostly AppSec and cloud security engineers who have learned how AI systems fail, plus one or two people who know models well. Most of the controls in the course are identity, authorisation, input handling and supply chain, applied to a new kind of component.

### Starting from nothing: the first 90 days

A new head of AI security at a company with AI features and no programme has no gateway, no intake and no numbers. A sequence that works:

- **Days 1 to 30: find out and stop the worst.** Build a first inventory from what already exists: model provider bills and expense claims, DNS and proxy logs for provider domains, the list of apps connected to the company's identity provider, and asking each engineering lead. Find the three features that can act or have the trifecta, and review those first. Make the quick fixes that need no platform: provider storage settings, keys moved out of apps, a scope taken away. Publish a one-page rule for staff, with an approved tool.
- **Days 31 to 60: make it repeatable.** Write the intake and the tier rule (P2) and run every known feature through them. Put new features on a gateway, bought or built (P1), even before old ones move. Start the security eval cases for the tier 3 features (note 5).
- **Days 61 to 90: show it and plan it.** The first board page (step 5), even with gaps. The roadmap and its "not doing" list (step 6). The first champions trained. The first red-team exercise on one tier 3 feature (note 10).

What does not happen in 90 days: blocking every direct provider call (that needs the gateway in place for everyone first, or it stops the business), an ISO/IEC 42001 certificate (P6), or a review of every feature. Saying so at the start keeps the plan believable.

## OWASP risks in this note

The codes come from the [OWASP Top 10 for LLM Applications](https://github.com/rajumandala/aisec-notes/blob/main/A1.%20OWASP%20Top%2010%20for%20LLM%20Applications.md) and the [OWASP Top 10 for Agentic Applications](https://github.com/rajumandala/aisec-notes/blob/main/A2.%20OWASP%20Top%2010%20for%20Agentic%20Applications.md), both 2026 editions. Nothing in this note has been run, so each example shows what would happen.

### LLM01: Prompt Injection

- **Example:** The team reports a falling attack success rate for the order assistant, quarter after quarter. A new red teamer gets in with the first technique they try.
- **Issue:** The fixed suite was tuned to, so its number measured the suite, not the defence.
- **Fix:** A fresh suite each quarter from new people, and a report on how many attacks were stopped by code rather than by the model.

### LLM03: Excessive Agency

- **Example:** Every feature has a current review, and coverage is 100%. One of them is an agent with client data and an email tool, and its review accepted the risk without a limit.
- **Issue:** Coverage measured that reviews happened, not what a fooled model could do.
- **Fix:** The exposure table for every tier 3 feature, and "features with an unbounded worst case" on the board's page.

### ASI10: Rogue Agents

- **Example:** Note 14's signal for orders after news reads exists, but its alerts go to a channel nobody reads.
- **Issue:** A control that exists on paper but would not catch an agent acting outside its job.
- **Fix:** A canary each quarter that should trip the signal, with time to detect reported.

### LLM06: Unbounded Consumption

- **Example:** The kill switch for the morning watcher works in a test. In a real drill it takes 50 minutes, because the person with access is on leave.
- **Issue:** Time to stop was assumed, never measured.
- **Fix:** A quarterly drill per tier 3 feature, with the minutes reported, and more than one person able to pull the switch.

## Problem and next step

**Problem:** the numbers show what is covered and how the controls hold up against the team's own tests. But the team writes its own tests, and the broker has not had a serious AI incident yet. How does it know its tests look like real attacks, and that its controls would have stopped what has already happened elsewhere?
